FL-04 Orchestrator

Upgrading Architectural Decision Record (ADR) documentation: from a fixed workflow toward an agent.

The Problem

Architectural Decision Records (ADRs) were being produced through a manual "Draft → Red Team → Revise" loop: one model drafts the ADR, a second model critiques it against a fixed checklist, and the first model revises. Every document goes through all three steps regardless of how trivial or complex the change is, which wastes time and tokens on small updates.

Current State: A Workflow, Not an Agent

As it stands today, FL-04 is a workflow, not an agent. The sequence of steps is hardcoded — draft, critique, revise — and neither model decides when to skip a step or call a tool. It's an evaluator-optimizer pattern: the code, not the LLM, controls the path.

The screenshot below is the local inference server (vLLM) that serves the open-weight model behind this pipeline, handling the /v1/chat/completions calls for each draft/critique/revise step.

The Planned Upgrade: An Orchestrator Agent

To make this an agent, control has to move from the hardcoded sequence into the model itself. The concrete upgrade is an Orchestrator Agent that looks at the size of a change first: minor vs. major is decided by a diff-size threshold (lines/files touched by the change) — below it, the agent drafts and finalizes in one pass, skipping the red team; above it, the agent pulls in extra context (searching the codebase, checking related ADRs) before drafting, and only then decides to invoke the red-team critique. This part is designed, not yet built — the current live pipeline is still the fixed three-step workflow described above.
